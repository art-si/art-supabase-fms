## 项目定位

亿企工场 FMS 是亿企工场的财务管理业务应用。它不是孤立的财务页面集合，而是以运输单据和企业经营活动为来源，覆盖结算、资金、核算、报表与高风险反向操作治理。

本仓只维护 FMS 页面、业务 API、领域类型与适配代码。登录、租户、菜单、权限、布局、路由、公共组件、Store 和 Supabase 公共客户端由 [`art-supabase-pro`](https://gitee.com/art-si/art-supabase-pro) 统一提供。

| 领域     | 已覆盖能力                                                                 |
| -------- | -------------------------------------------------------------------------- |
| 运输财务 | 客户/承运商对账、应收账龄、收付款、发票、运单费用、利润分析                |

| 智能辅助 | 发票/票据 OCR、费用识别、合规复核、回款风险建议与核算准备检查              |

## 业务闭环

```text
运输与经营单据
  → 对账 / 应收应付 / 费用
  → 收付款 / 核销 / 发票
  → 凭证草稿 / 审核 / 过账
  → 账簿 / 报表 / 期末结账
  → 经营分析与异常治理
```

OCR 与 AI 只提供可复核的录入和分析建议；付款、过账、结账、反结账等高风险动作仍由有权限的人员确认，并由服务端权限与审计边界约束。

### 多账套自动入账约束

资产、折旧批次、薪资批次、税务期间和商业票据的入账事件继承来源记录的账套。服务端从对应业务表读取账套并验证租户一致性，不接受事件载荷指定的任意账套；缺失或跨租户来源必须拒绝。其他未明确归属账套的业务来源沿用租户默认账套规则。

2026-10-03 已通过正式重试接口验证两条资产转固和两个折旧批次：分别生成借贷平衡的两条分录，金额为 1200、2400、60、60。账套继承与跨租户拒绝经过事务回滚验证，内部解析函数仅授予数据库所有者执行权限。此记录仅证明该流程，不代表整个 FMS 的增删改查验收完成。

### 出差申请审批与关联报销

出差申请通过统一 `start_workflow` 发起 `fms_travel_application` 审批。服务端从原单解析租户，在返回已有审批实例前检查 `FinanceTravelApplication:Submit` 与填单人身份；新提交还会锁定原单，校验草稿或驳回状态、有效行程和行程金额合计。审批回调维护审批中、通过、驳回和撤回状态、核定金额及拒绝意见。驳回后可以修改并重新提交，审批中及通过后的申请通过只读入口查看。流程设计器提供出差审批模板，审核节点需由管理人员配置并发布，不会自动通过或修改既有审批定义。

通过后的申请可下推差旅报销。`prepare_fms_travel_application_reimbursement_secure` 同时校验来源查看/下推与目标查看/新增权限，继承原申请租户、申请人和费用承担部门，带入行程费用预算。报销保存及提交继续校验关联申请的租户、申请人和已通过状态；实际费用、发票及收款资料需要重新核对。新增权限只登记目录，不自动授予现有角色。审批回调不向浏览器角色授予直接执行权限。

`tests/integration/fms-travel-application-workflow.sql` 用两条事务内临时记录验证回调状态及金额、匿名入口拒绝和私有回调执行权限，结束后回滚；该检查不等于真实账号完成审批。`tests/e2e/travel-reimbursement-push.spec.ts` 验证两条申请带入报销、保存失败重试及来源/租户载荷；`tests/e2e/expense-submit-context.spec.ts` 覆盖确认期间撤权或切换租户后不提交。接口接通、隔离回归与真实流程签收分别记录，尚未将两条真实新申请的完整审批及报销闭环记为通过。

出差申请、借款和还款列表的“当前处理人”由当前审批节点的有效待办同步维护，随分配、转交和节点切换更新，流程结束后清空，不再使用提交操作人的姓名。内部同步函数不向浏览器角色开放；`tests/integration/fms-workflow-current-handler.sql` 以六条临时记录覆盖三类单据，验证分配、转交、已处理待办、下一节点及流程结束，全部回滚。

### 人人费用还款单

还款单以 `fms_travel_repayment` 为主单、`fms_travel_repayment_item` 为关联借款明细、`fms_travel_repayment_receipt` 为不可覆盖的逐笔收款流水。关联借款必须已付款；服务端锁定借款行后，由 `app_private.fms_travel_loan_settlement` 按已付款、实际收款、已审核抵扣及已提交未结算预留计算余额，草稿不占用额度，提交时重新校验。借款展示缓存由同一结算口径刷新；分次收款只预留未收部分，避免重复扣减。同一借款明细可拆分多笔归还，但合计不得超过该明细原借款金额。当前借款金额字段以人民币元计，明细币种与本位币均为 CNY、汇率为 1；引入多币种借款时必须同步调整来源字段和校验，不得只开放前端币种输入。

还款草稿由 `save_fms_travel_repayment_draft_entry_secure` 保存；内部三参数函数不授予 `authenticated` 执行权限。提交接口原子地校验余额并启动 `fms_travel_repayment` 审批实例，未发布审批定义时保留草稿。审批回调将单据推进到已审核或已驳回；确认收款按金额写入流水，并更新还款单已收款额及借款已还款额、未还余额。业务表向浏览器只授予读取，写入需通过带租户和按钮权限校验的 RPC。删除仅允许草稿，并经 `MasterDataDeleteGuard` 检查引用。

借款付款经 `record_fms_travel_loan_payment_secure` 校验审批状态、租户、按钮权限、收款明细、资金账户、金额上限和幂等请求标识。真实付款写入资金日记账；演示付款仅允许明确标识的测试收款账户与界面验收资金账户，付款记录标为 `is_demo`，不生成真实资金流水。演示借款只能走演示付款；关联的还款与收款也沿用演示标识。

`tests/integration/fms-travel-loan-payment.sql` 以回滚事务验证模拟付款幂等、金额上限、测试账户限制与资金流水隔离；`tests/integration/fms-travel-repayment.sql` 以回滚事务验证草稿编辑、超额拦截、已发布流程启动、审批回调、分次收款、租户范围和报销抵扣。真实资金付款与银行入账没有在演示流程中执行。

```powershell
pnpm install
pnpm dev
```

```powershell
pnpm check
pnpm build
pnpm preview
```

## 与主仓协作

FMS 业务修改在本仓提交并推送，随后在主仓更新 `modules/art-supabase-fms` 子模块指针。跨模块读取使用用途明确、字段最小化、租户隔离的 API/RPC 契约；FMS 不直接导入其他业务仓源码，也不复制主平台公共运行时。

## 安全原则

- 页面可见和按钮可用不代表后端授权，数据库 RLS 与服务端校验是最终边界。
- 制单、审核、过账、付款、核销、结账及反向操作应拆分权限并保留审计。
- 前端只使用 Supabase `anon` / publishable key，不暴露 `service_role` 或第三方服务密钥。
